# 测试量预算（设计方案）

- 定位：本档回答「技能已有测试规则，采用方为什么仍会反复跑测试、本仓为这条判据改什么」。**不属于本档**：各采用方测试框架的选型；门禁结果的增量缓存（本批不做）。
- 来源（只读实测，不复制原文）：采用方 CLWriting-Mac 的 `AGENTS.md` 测试分层、PMS 的《测试与提交》三档门禁、PMS 与 DSH-QTrans 的 `check-all` 门表、本包 `run-gates.ts` 的调度实现。
- 判据：一条改动入选的条件是「它约束测试的**次数与时机**，而不是测试的**内容与写法**」——后者已由 `references/test-reliability.md` 与 `verify-test-hygiene.ts` 覆盖。

## 一、事故面

采用方的现象是「测试停不下来」：改一处、跑一遍、再改、再跑。规则不是缺失，而是作用域只覆盖终点：

| 现有规则 | 覆盖的时刻 | 漏掉的时刻 |
|---|---|---|
| `pre-push.md`「不要重复已经通过的检查」 | 推送前 | 实现过程中 |
| `SKILL.md`「提交前的证据选择」 | 提交前 | 实现过程中 |
| `test-reliability.md`「拒绝掩盖型修复」 | 红了之后怎么修 | 红了几次之后该停 |

下游已经各自补了这一层：CLWriting-Mac 在 standing orders 里自建 L0/L1/L2，PMS 在规范档写「过程中只做编译级检查」。同一条规则被两个采用方各写一遍，按「一个事实一个家」，它该住进技能。

运行器侧还有一个放大器：`run-gates.ts` 的主入口硬编码 `failFast: true`。`check-all` 里相互独立的门，第一个失败后未启动的直接记为 skipped；修一个再跑，才发现下一个。文档门先红时，`go test` 与构建根本没启动。N 个违规等于 N 次全量。

## 二、判据：测试量是独立的一层

测试的规则分三层，不能互相代替：

1. **写不写**：一条改动等于一条回退即变红的用例，断言只锚对外可观察面（已有）。
2. **跑多少**：零测试面不跑；过程中只做编译级检查；提交时一次证据运行（本批新增）。
3. **怎么修**：失败分诊、拒绝掩盖、假设上限（已有，补后两项）。

「跑多少」不能从「按改动面选证据」推出来：后者回答「跑哪条」，不回答「跑几次」。一个 agent 可以每次都选中正确的测试文件，然后把它跑十遍。

## 三、决定清单

**一、测试量预算住 `references/test-reliability.md`，不新开档。**

- 结论：在该档开头新增「先决定跑多少」一节：三档（零测试面／过程检查／证据运行）、一个内容状态一次证据、重跑合法的三种情形、失败分诊四分法、同一失败两个假设的上限。
- 最强替代：新开 `references/test-budget.md`。否决理由——测试的「量」与「可靠性」是同一个决策的两面，分成两档会让「这次该不该跑」与「红了怎么办」各自只读一半；新增一档还要同时改任务表、描述与采用方指针，收益不抵成本。
- 次强替代：只写进 `SKILL.md` 正文。否决理由——正文是摘要，细节需要有可展开的家；正文只留判据与指针。

**二、`SKILL.md` 合并「测试」三条判断，任务表加一行。**

- 结论：把「测试可靠性」一节改写为「测试：写不写、跑多少、怎么修」，三条判断并排；任务表加「决定跑多少测试、何时停」一行指向同一档。
- 最强替代：只改 reference，正文不动。否决理由——客户端只自动加载正文；正文不提，采用方的 agent 不会知道有这条规则。
- 次强替代：新增独立小节「测试量预算」。否决理由——两条小节都指向同一份 reference，读者要自己合并；一个事实一个家，也该是一个主题一节。

**三、AGENTS 模板加一行。**

- 结论：`templates/AGENTS.{zh,en}.md` 的「门禁」节加一句：过程中只做编译级检查，决定提交时跑一次覆盖本次改动面的证据档，只有横跨整个仓库才跑全量，同一内容状态不重跑已通过的检查。
- 最强替代：让采用方自己从 reference 里发现。否决理由——standing orders 是每次会话都在上下文里的唯一一层；两个采用方已经证明，不写在这里就会被各自重写。

**四、`run-gates.ts` 默认 keep-going，`--fail-fast` 改为显式开关。**

- 结论：主入口默认 `failFast: false`；新增 `--fail-fast` 参数；`needs` 继续承担真正的依赖阻塞。一次运行把相互独立的门的失败全部报出来。
- 最强替代：保持默认 fail-fast，只靠规则要求「修完一批再跑」。否决理由——规则管不住调度：agent 看不到未启动的门的失败，只能再跑一次；这是工具形态在制造循环，不该让文字替它背锅。
- 次强替代：给门禁结果做内容哈希缓存。否决理由——测试正确性还依赖环境（工具链、端口、并发），缓存会把「这次没跑」伪装成「这次通过」，违反门禁的诚实边界；本批只改调度，不引入状态。
- 代价：CI 上一次失败后仍会跑完其余独立门，机器时间变多。需要快速失败的采用方在 CI 命令里显式加 `--fail-fast`。

**五、负向对照限定为「新增或修改门禁规则」。**

- 结论：在测试量预算一节写明：一红一绿是**门禁规则**的验收预算，不是每个行为改动的预算；普通改动的证据是「拥有该行为的用例通过」，不要求先制造红。
- 最强替代：维持现状，让 agent 自己判断。否决理由——正文的「门禁必须证明会失败」没有限定范围，实测会被推广成每个改动都先红后绿，正好翻倍。

## 四、验收

- `npm test` 全绿；新增一条 CLI 用例覆盖两种模式：默认模式下独立门在首个失败后仍运行；`--fail-fast` 下未启动的门记为 skipped 且原因点名。
- 正向：`node skills/dsh-project-harness/scripts/run-gates.ts text` 通过；反向：把默认改回 `failFast: true`，新用例必须红。
- 文档门：`verify-doc-index.ts` 认新档；`docs/README.md` 的篇数同步。
