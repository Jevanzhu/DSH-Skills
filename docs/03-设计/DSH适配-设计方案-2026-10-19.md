# DSH 适配（设计方案）

- 定位：本档回答「什么叫技能在客户端里被完整加载、本仓为这条判据改什么、每条改动的替代方案与否决理由」。**不属于本档**：DSH 客户端自身的待办与发布节奏；采用方仓库的文档链改造（那是升级安装加各自落位的事，见执行档）。
- 来源（只读实测，不复制原文）：采用方 CLWriting-Main 的会话记录（技能目录条目、`skill` 调用与否、子 agent 会话）、本机安装包 `resources/app.asar` 内 `@deepseek-ai/dsh-skill-filesystem` 与 `@deepseek-ai/dsh-tool-skill` 的实现。
- 判据：一条改动入选的条件是「去掉 DSH 与采用方的专名后仍然成立」——描述长度上限、指针跟随、派发面自带落位，这些在任何「目录常驻、正文按需」的客户端上都成立。

## 一、事故面：两种失败，不是一个问题

采用方出现的现象是「技能没起作用」，实测把它拆成两类，根因不同：

| 失败形态 | 现场证据 | 根因 |
|---|---|---|
| 根本没加载 | 首轮审计会话 0 次 `skill` 调用，产出落在文档链外 | 任务在模型看来像「一次性评审」，目录里只有 name + description，描述尾部触发词被截断，路由没命中 |
| 加载了没照做 | 次轮调用了 `project-harness`，仍把报告写在仓根 | 正文只是摘要，`references/` 未被跟随；派发任务书里「禁读一切文档」把链规范一起挡在门外 |
| 子 agent 全未加载 | 当日 33 个子会话 0 次 `skill` 调用 | 技能正文不继承给子 agent，它们只拿到任务书 |

三类里只有第一类能被本仓的改动影响；第二类一半是本仓的「摘要 + 指针」形态没写清跟随义务，一半是派发口径；第三类是派发纪律，不是技能内容问题。

## 二、判据：完整加载是两段，不是一步

客户端把技能分两段给到模型：**目录常驻**（每个技能一行 name + description，随会话注入）与**正文按需**（模型判断相关后调 `skill` 工具取 SKILL.md 正文）。`references/` 与 `templates/` 两段都不进——它们是第三段，只能由正文里的指针把人带过去。

由此得到三条可判命题，本方案每条对应一个改动：

1. 描述是**路由面**：它必须短、触发词必须前置，否则技能永远不被选中。
2. 正文是**索引**：它必须写明「这个任务先读哪几个指针」，否则正文读完就等于只加载了摘要。
3. 派发是**唯一的继承通道**：子 agent 只有任务书，落位与验收命令必须由派发书写进去。

## 三、决定清单

**一、description 压到客户端上限内，并中英双写触发词。**

DSH 的目录渲染有上限（`catalogDescriptionMaxLength` 默认 500 字符），超出截断加省略号。实测两个技能的描述分别是 747 与 648 字符，尾部触发词（「派活判据」「归档巡检」一类）对模型不可见。

- 结论：两个描述改写为规范化后不超过 500 字符，触发词前置、中英并列，尾部只留「何时用」的补充。
- 最强替代：调大客户端 `catalogDescriptionMaxLength`。否决理由——采用方不控客户端配置，且该配置是全局的，调大等于把所有技能的目录一起撑长，占用每轮固定上下文；上限存在本身是防止目录膨胀的设计。
- 次强替代：把尾部触发词搬到可选的 `whenToUse` 字段。否决理由——目录渲染只取 name + description，`whenToUse` 不进路由面，等于换个地方藏起来。

**二、保持「摘要 + 指针」，不把 references 内嵌进 SKILL.md。**

- 结论：正文只留判据与指针，`references/` 继续是细节的家；新增一节「加载与使用前提」，把「正文不会自动带来 references，按任务类型先读哪几份」写成显式表格。
- 最强替代：把 `references/` 的关键判据复制进正文，一次加载就什么都有。否决理由——一个事实一个家，两处副本必然分叉；且每次加载都付全文的上下文成本，而排障类细节只在少数任务里需要。
- 次强替代：在 description 里写「使用前必须读 references」。否决理由——描述是路由面，加载纪律写在那里既不保证被读到，又挤占本就紧张的 500 字符。

**三、机制细节与失败模式单独成档 `references/client-loading.md`。**

- 结论：加载两段模型、六档根的优先级、目录里放什么、描述为什么是路由面、四种断点、怎么验证真的加载了、其他客户端差异，全部住这一份参考档；SKILL.md 只放一行指针。
- 最强替代：写进 SKILL.md 正文。否决理由——正文是常驻说明，读者是「正在用技能的人」；机制只在换客户端、排障、以及写描述时需要，属于按需面。
- 次强替代：写成独立的第三方文档，不进技能。否决理由——离开技能分发的文档读不到；采用方装的是副本，指针必须跟着副本走。

**四、把「描述长度与目录一致性」做成门禁 `verify-skill-catalog.ts`。**

- 结论：新增一道文本门，核对声明的技能根下每个技能档的 frontmatter：name 必填且 kebab-case 且与目录同名，description 必填且规范化长度不超过 manifest 声明的上限，声明的根必须存在，扫到零个技能档判红（空面不算通过）。manifest 缺省 `{}` 表示本仓不声明技能根。
- 最强替代：写进评审清单，靠人看。否决理由——这正是事故形态：失败是静默的（技能装上了、目录里也有，只是永不命中），没有红灯就没有反馈闭环；而长度与命名是可机械判定的，按本仓纪律不该交给评审。
- 次强替代：只在 `structure.spec.ts` 加一条仓内测试。否决理由——采用方装的是一份副本，他们不会跑本仓的测试；走 bootstrap 复制才能让采用方也有这道门。

**五、派发面：模板加四格，判据加一节。**

- 结论：新增 `templates/agent-brief.{zh,en}.md` 派发任务书模板，在靶点、验收判据、不读面之外补交付面（落哪个槽位或路径、索引与活账是否同批更新）、技能前置、禁止、报告格式；`references/agent-work.md` 补一节「技能不继承」，说明「按某某规范做」等于没写。
- 最强替代：在派发时口头要求子 agent 先加载技能。否决理由——子 agent 的上下文里没有父会话的技能正文，也没有「父会话加载过」这一事实可推理；任务书是唯一通道。
- 次强替代：把交付面并进「验收判据」一格。否决理由——落位失败与验收失败是两种偏离：产物落在链外时所有门都扫不到，验收命令却可能是绿的。两格分开才能各判各的。

**六、安装根不迁移，命令写 `<skill-dir>`。**

- 结论：技能继续装 `.agents/skills`（跨客户端共享根），不迁 `.dsh/skills`；文档里的命令一律写 `<skill-dir>/scripts/bootstrap.ts`，不写死 `~/.agents/skills/...`。
- 最强替代：迁到 `.dsh/skills` 拿更高优先级。否决理由——失去跨客户端共享，而本仓没有压过同名技能的需求；优先级只在同名冲突时有意义。
- 次强替代：保留 `~/.agents/skills` 写法并在旁注「可能不存在」。否决理由——实测该目录整棵不存在，逐字执行会 ENOENT；文档里的命令应当可直接执行。

## 四、边界与诚实声明

门禁只能判**「能被加载」**：描述长度、命名、目录一致、双语成对。它判不了「是否被调用」与「调用后是否照做」——后者是语义遵守，落在评审与派发纪律上，没有门兜底。这与本仓既有的诚实边界同形：绿灯意味着在这些确切内容上确认过一致性，不意味着确认本身可靠。

## 五、重访条件

- 客户端把目录渲染字段扩到 `whenToUse` 或调大上限：描述收紧的尺度与触发词位置要重算。
- 技能数量涨到目录预算成为瓶颈：需要的是目录摘要纪律，不是再加描述。
- 采用方出现「加载后仍不照做」的新形态：先补派发模板与判据，不为语义遵守造伪门。
