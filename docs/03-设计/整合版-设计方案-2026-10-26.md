# 整合版（设计方案）

- 定位：本档回答「两个 skill 整合成单包意味着什么、每条整合决策改什么、替代方案与否决理由」。**不属于本档**：两个源 skill 自身的行为改动（整合的前提是源结构与行为不动）；workbuddy 客户端的实测结论（未实测，见活账）。
- 来源：本仓 DSH 适配批次（`aa10f00`）确立的「目录常驻、正文按需」客户端判据；采用方单副本安装的诉求。
- 判据：一条改动入选的条件与 DSH 适配同形——「去掉客户端专名后仍然成立」：单目录包、标准 frontmatter、描述预算，这些在任何「扫描 `.agents/skills` 根、按 name + description 路由」的客户端上都成立。

## 一、目标形态

`skills/dsh-project-harness/` 是第三个 skill：单一目录包同时承载 `agent-notes` 与 `project-harness` 的全部 references、scripts、templates，加一份合并叙述的门面 `SKILL.md`。两种形态并存且能力等价：单副本安装选整合版，两个独立技能条目选分离版；升级路径同源（分离版改了什么，重跑构建即进整合版）。

## 二、决定清单

**一、整合版是构建镜像，不是手写的第三份。**

- 结论：三个资源目录由 `scripts/build-integrated.ts` 从两源逐字节镜像（源删则删），生成物提交进仓；`--check` 即一致性校验，`structure.spec.ts` 复用构建器自己的 diff 函数钉住同一规则。
- 最强替代：手写维护第三份。否决理由——同一规则住两处必然分叉；本仓的纪律是门禁钉字节，不是靠人同步。
- 次强替代：安装时现场合成（采用方脚本拼两源）。否决理由——采用方拿到的是副本，副本必须离仓自洽；现场合成要求两源同装，等于没整合。

**二、SKILL.md 是人写门面，不参与构建。**

- 结论：构建只镜像资源目录；门面正文手工维护——合并两源正文、两张「先读」表合一、互相推诿的「责任边界」改写为「整合与上游」。一致性由资源逐字节、`verify-skill-catalog`（name 与描述预算）、`verify-md-links`（指针全有效）与评审兜底。
- 最强替代：脚本按节拼装两源正文生成。否决理由——正文是散文，接缝的语义（哪里并表、哪里删推诿）不可机械判定；源正文任何结构调整都要改拼接逻辑。
- 次强替代：门面逐字节引用源正文。否决理由——两源正文各自含指向对方的「责任边界」，照抄则自相矛盾。

**三、spec 文件不进整合版。**

- 结论：`*.spec.ts` 排除在镜像外。spec 断言的是源布局的语义（兄弟目录存在、部分安装拒绝），在整合布局下语义翻转或死重；且 spec 是本仓自测，不是采用方安装面。
- 最强替代：一并镜像。否决理由——镜像出的 spec 在整合布局下不可运行，是误导。

**四、bootstrap 同目录回退，源布局行为不变。**

- 结论：`bootstrap.ts` 的 `AGENT_NOTES_SKILL` 兄弟目录存在时优先兄弟目录，否则回退脚本同目录。仓内唯一的跨 skill 硬路径就这一处；回退后 paired 前置检查照常 fail-closed（整合布局缺配对文件仍拒绝）。
- 最强替代：构建时对 bootstrap.ts 做文本变换。否决理由——整合版与源不逐字节，一致性规则要养「已知变换」例外，变换本身脆弱。
- 次强替代：bootstrap 按目录名探测布局。否决理由——采用方可改目录名安装，探测即猜测。

**五、平台中立形态，workbuddy 差异实测后补。**

- 结论：整合版按通用形态做：`.agents/skills` 共享根、name 为 kebab-case 且与目录同名、description 归一后不超过 manifest 声明的 500 上限。DSH 侧已被既有门禁与实测覆盖；workbuddy 立活账待办，不预设差异。
- 最强替代：为 workbuddy 专门适配。否决理由——无实测依据的差异适配是猜测；DSH 适配的教训是先有事故面或实测再动手。

**六、命名 dsh-project-harness。**

- 结论：名字由仓主拍板带 DSH 前缀；客户端的 name 正则 `^[a-z0-9]+(?:-[a-z0-9]+)*$` 只认小写，故目录与 name 字段用全小写 `dsh-project-harness`。
- 最强替代：平台中立的泛名（agent-harness 一类）。否决理由——仓库名即 DSH-Skills，DSH 在本仓语境是技能体系名而非某客户端专名；命名权在仓主。

## 三、边界与诚实声明

构建只保证资源与源逐字节一致；门面正文与两源正文的叙述一致性不在机器判定内（指针有效性由 `verify-md-links` 钉，叙述漂移靠评审）。workbuddy 兼容是按标准形态的推断，未经实测——「能被 DSH 加载」有门禁与端到端验收，「能被 workbuddy 加载」目前只是形态论证。

## 四、重访条件

- workbuddy 实测出现差异（描述上限、根目录、frontmatter 字段）：按差异补批次，本档的形态判据不因此推翻。
- 两源出现同名资源且字节不同：构建 fail-closed 拒绝；届时要么把它统一为两源共享的逐字节一致文件，要么改名让路。
- 门面与两源正文的叙述漂移成为实际负担：重访「门面生成」决策（让正文可由源拼装），而不是放宽资源一致性门禁。
