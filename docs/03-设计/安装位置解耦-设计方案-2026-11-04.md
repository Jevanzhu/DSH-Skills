# 安装位置解耦（设计方案）

- 定位：本档回答「技能装在不同位置（项目级、各客户端用户级）时，哪些生成物会把位置固化、换位置要改什么」。**不属于本档**：客户端如何发现技能（见 [client-loading.md](../../skills/dsh-project-harness/references/client-loading.md)）；多份副本的版本同步机制（未决，见活账）。
- 来源（只读实测）：把技能复制到模拟用户级根后，从两个不同安装路径各跑一次 bootstrap，对目标仓做逐字节 diff；再对生成的 manifest 手工制造「根被移走」与「根为空」两种输入，观察门禁结果。
- 判据：一条改动入选的条件是「它决定了安装位置会不会被写进项目内容」——只是运行时读取位置的不算，那份信息本来就该由客户端给。

## 一、实测：生成物本身与位置无关

同一版本、不同安装路径各跑一次 bootstrap（一次从源码仓，一次从模拟的 `~/.claude/skills/`），目标仓 `diff -r` 为空，且生成文件里搜不到任何绝对路径。结论：**脚手架、门禁副本、manifest、版本记录都不带位置**，`version.json` 只写版本号。

所以「换安装目录要改项目文件」不是普遍现象，只有三个具体入口会把位置带进去：

| 入口 | 造成什么 |
|---|---|
| 提示文本打印 `SKILL_ROOT` 绝对路径 | agent 把提示抄进 `docs/` 或活账，机器路径就此入库 |
| `skill-catalog` 的提示「把 `.agents/skills` 加进 roots」 | 采用方照做后，技能一搬到用户级，根缺失或为空，门禁转红 |
| 文档把 `<skill-dir>` 定义成 `<repo>/.agents/skills/...` | 换位置后照着文档敲的命令全部指向不存在的目录 |

## 二、决定清单

**一、安装位置不是项目内容。** 文档以用户级安装为默认；项目级安装降为「需要钉版本、或 CI 里没有技能」的例外，并写明它会遮蔽用户级同名技能。

- 最强替代：保持项目级为默认。否决理由——同一份技能在三个客户端里需要三个项目副本，且每加一个客户端就要往仓库里多放一份；这正是「不同安装路径要改项目」的来源。
- 次强替代：两种并列，让采用方自选。否决理由——并列等于没有默认，而两处同时存在会产生遮蔽，必须有一句裁决。

**二、bootstrap 的提示不打印绝对路径。** 改成「this skill 的 `templates/` 目录」加相对文件名。

- 最强替代：维持绝对路径。原注释的理由是「模板不在目标仓里，相对路径会被误读」。否决理由——这句话进了项目文件就是把一台机器的路径固化；而 `<skill-dir>` 在加载时已经由客户端交给 agent，读者不缺这个锚点。
- 次强替代：打印相对于技能目录的路径。否决理由——仍是机器路径，只是短一点。

**三、空技能根是正常状态。** `skill-catalog` 的提示改写为「技能装在用户级时这是正常状态，只有仓内自带技能才声明根」；缺失根的报错补一句「用户级安装不属于本仓——删掉这个根，而不是建目录」。

- 最强替代：门禁对缺失根宽容（警告不红）。否决理由——声明了却不存在，说明申报与现实脱节；这正是门禁该红的事。改提示而不是改判据。

**四、不做安装脚本，也不做客户端识别。** 安装是用户级的一次性动作，用一段 shell 就够；「当前是哪个客户端」不是可靠信号——实测 CodeBuddy 同时设置 `CLAUDE_*` 与 `CODEBUDDY_*`，按环境变量判断会误判。真正可靠的是副本自身位置（`import.meta.url`）与显式参数，而这两者只回答「升级改哪份」，不回答「该写进哪个根」。

- 最强替代：`scripts/install.ts` 枚举各客户端根并建入口。否决理由——它把「这台机器装了哪些客户端」变成技能的知识，而这是用户的配置；一段 shell 在同一处表达得更直接，也不会随客户端增减而失效。

## 三、验收

- `npm test` 全绿，`npm run check` 全绿。
- 空仓跑 bootstrap，输出里不含 `/Users/` 或任何安装根路径。
- 在目标仓声明 `roots: [".agents/skills"]` 后删除该目录：门禁红，且报错含「删根而不是建目录」。
- 同一目标声明 `{}`：门禁绿，打印 `nothing to check`。
