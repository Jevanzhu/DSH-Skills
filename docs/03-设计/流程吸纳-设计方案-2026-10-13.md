# 从 CLW 吸纳流程（设计方案）

- 定位：本档回答「吸纳哪些流程、以什么形态落进本仓、按什么批序」。**不属于本档**：CLW 的知识层与产品数据（整体排除）；CLW 本体何时接入本 skill（采用方自己的后续事项）。
- 来源（只读参考，不复制内容）：CLWriting-Main 根 `AGENTS.md` 的恒常纪律、`Dev/Docs` 的文档链现状与 `05-规范` 的文档操作链、`scripts/check-*.mjs` 门禁头部的判据文本。
- 准入测试：拟纳入的每条规则，去掉「CLW」字样与项目数字后必须仍然成立；通不过就留在 CLW，不进本仓。

## 一、目标与边界

本仓是**底座**：机制（门禁、台账、归档、链）与判据（判断什么、为什么）。CLW 是**首个复杂采用方**：它跑通的流程被提炼成通用规则回到本仓，它自己的数据留在 CLW。

吸收的是**流程与判断**，不是**数据**：门禁脚本里通用的是判据（判什么、何时 fail-closed），项目特有的是名单与数字（上锚值、目录专名、篇数）。前者入库并配负向对照，后者作为采用方的实例配置——通用性与具体性分开，采用方升级时不丢配置。

## 二、三面模型

文档治理因此分三面，这是本批次的结构性结论：

| 面 | 管什么 | 落点 |
|---|---|---|
| 常驻面 | 规则住哪、写多长、一段一行、链接与扫描范围 | `references/doc-governance.md` |
| 工作链 | 一件事从提出到了结走哪些档、怎么命名、怎么记档、怎么归档 | `references/doc-lifecycle.md` |
| 冻结面 | 已交付决策的封存与哈希校验 | `agent-notes` 的 `archived/` |

分工判据：**事实的家**归常驻面，**过程与交付**归工作链，**做过的决定**归冻结面。同一件事在三面各留其形，不互相抄写——抄写即第三份副本。

## 三、CLW 现状到槽位的映射

CLW 的 `Dev/Docs` 已经是链的形状，与本仓八槽位一一对上。这既是模型正确性的旁证（它从真实使用里长出来），也给采用方一份默认映射：

| 本仓槽位 | CLW 现状 | 可移植的做法 |
|---|---|---|
| 索引 | `Dev/Docs/README.md` | 目录导航 + 每槽位状态行 |
| 活账 | `00-总览.md` | 未了结事项表 + 维护约定 |
| 评审 | `01-评审/` | 评审者署名进文件名，结论三出口 |
| 执行 | `02-执行/` | 全局序 + 批次靶点/动作/验收，末节回填 commit 号 |
| 设计 | `03-设计/` | 定位行 + 不属于本档清单 + 被否决的替代方案 |
| 调研 | `04-调研/` | 外部事实与可行性结论，决策另立设计档 |
| 规范 | `05-规范/` | 长期操作规范，从执行档提炼后删除原处 |
| 归档 | `Archive/` | git 复原锚核验、commit 号留痕、直删不打包 |

## 四、吸纳清单（五族）

**族一：文档治理（批 1）。** 从文档链现状与文档操作链规范提炼：八槽位与「不属于这里」、命名四段、活账文法、评审三出口、归档三关、索引校验。落点 = `references/doc-lifecycle.md` + `verify-doc-index.ts` + `templates/ledger.md`、`templates/docs-index.md`。

**族二：注释卫生（批 2）。** 从注释检查脚本的头部判据提炼：标签族（TODO 一类标记）的登记与豁免声明、注释残留物、默认 fail-closed（无法判定时拒绝而不是放过）。落点 = `references/comment-hygiene.md` + `verify-comment-hygiene.ts`：门拥有标签语法与豁免文法，标签名单是采用方配置。

**族三：测试纪律（批 3）。** 从计数检查脚本与既有测试可靠性判据提炼：账实对照（声明的数量与实际一致）、静态枚举纪律（文档里的清单由脚本从源头生成或校验，不手抄）、`.only`/skip 的禁止与守卫、执行顺序快照。落点 = `references/test-reliability.md` 扩节 + 对应门禁。

**族四：对账与发布（批 4）。** 从宣称数字与阈值双写的教训提炼：文档宣称的数字必须可核（对照源头，而不是对照另一份文档）；门禁下限规则（宁可少几条门，不可突破下限）；发版批纯度（一次发布只含一个主题，混批视为缺陷）；阈值只允许一个声明点——多处书写必然分叉。落点 = 门禁 + `references/gates.md` 与 `governance-model.md` 补节。

**族五：agent 工作纪律（批 5）。** 从根 `AGENTS.md` 的恒常纪律提炼：任务书三件（任务、必读、验收）、先定位后阅读、通读即专项、子 agent 并发上限、注释只写约束不写沿革。落点 = `references/agent-work.md`。

## 五、明确排除

- **知识层与产品内容**：那是采用方的应用数据，与项目管理流程无关。
- **CLW 的具体数字与名单**：上锚值、测试计数、目录专名——作为采用方配置留在 CLW。
- **采用方的仓库结构假设**：本仓不替采用方规定语言、包管理器与测试框架，边界不变。
- **整段搬运门禁脚本**：只搬判据与形态；脚本按通用规则重写，并逐条配负向对照。

## 六、批序与验收

批 2 至批 5 各自独立成批，收口条件相同：新门禁带负向对照（每条规则一变红）、规则与文档同批、`npm test` 全绿、本链同步记档（活账加行／摘行）。

批序的理由：族二、族三都是「单点判据 + 一个门」，形态最轻，先落可以把记档与负向对照的流程走顺；族四管的是门禁自身的下限，依赖前三族把门禁形态稳定下来；族五纯判据、无新代码，最后落，顺带统一前四批暴露出的措辞。

## 七、未决

- 本仓是否自装 harness（`.agents/notes` 与自举脚本、自身文档预算）：链已自举，决策记录面等真正用得上时再定。
- 族四的「发版批纯度」在单仓、无发布序列时如何验证：批 4 必须先给出可判形态，给不出就只作为评审判据写入，不假装有门。
