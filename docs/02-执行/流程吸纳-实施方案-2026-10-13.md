# 流程吸纳 执行方案

- 定位：执行正本——批序、每批的靶点与验收、执行记录（末节回填）。**设计理由不在本档**，正本 = [流程吸纳-设计方案-2026-10-13.md](../03-设计/流程吸纳-设计方案-2026-10-13.md)。
- 关系：设计档定族、边界与理由；本档只回答「谁先谁后、每批动什么、怎么算过关」。
- 全局序：**批 1 文档治理 → 批 2 注释卫生 → 批 3 测试纪律 → 批 4 对账与发布 → 批 5 agent 工作纪律**（**已全部完成**，commit 号见末节）。收口条件统一，见设计档 §六：负向对照齐、规则与文档同批、`npm test` 全绿、链上同步记档。
- 批外补充：**批 6 检查面单点收口**（来源是批 4／批 5 验收后的核查）与**本仓不设 CI**（作者决定）——均不在设计档批序内，见末节。

## 批 2：注释卫生（已完成）

- 靶点：注释只写约束与语义、修复史归 git；两族判据（标签形态与切除残形）缺一不可；字面量红线（字符串／模板／正则永不报告）；例外与承重锚注的显式登记；扫描面 fail-closed 且不入台账。
- 动作：`verify-comment-hygiene.ts`（逐字符状态机读注释面、台账接入）＋ 负向对照 21 例 ＋ `references/comment-hygiene.md`；接线 `run-gates`（doc-quick 第 5 条）／`bootstrap`（复制校验器、按实测目录植入起始规则、并入台账家族）／本仓 `check` 聚合（原 `check:docs` 更名，现含四道文本门）／本仓自用 manifest。
- 验收：21 条对照全绿；本仓 26 档、6 形态全绿；字面量反例在 spec 内钉死；门在本仓先行红过两处（示例注释写了具体日期），按判据改为占位符后转绿。

## 批 3：测试纪律（已完成）

- 靶点：表面绿而覆盖消失（`.only`、无条件 `.skip`）的形式判据；先判该不该写（一条改动 = 一条回退即变红的用例、断言只锚可观察面、并入优先、分层执行）；数字与清单的口径纪律（静态可复现、来源单一、从代码面取、宣称值失准即红、顺序快照）。
- 动作：抽出共享扫描器 `surface.ts`（注释面 + 代码面，一处实现，注释门与测试门共用）＋ `verify-test-hygiene.ts`（`.only` 一律红；`.skip` 首参为标题字面量或 `true` 即红，条件式环境门合法）＋ 负向对照 16 例 ＋ `references/test-reliability.md` 扩三节（该不该写 / 表面绿而覆盖消失 / 数字与清单）＋ 接线 `run-gates`（文本门组更名 textGates，doc-quick 第 6 条）／`bootstrap`（复制校验器与共享扫描器、按实测目录植入测试面、并入台账家族）／本仓 `check` 与自用 manifest。
- 归属调整（结论）：**账实对照的门禁形态与批 4 的「宣称数字可核」是同一机制**（一条宣称 = 文档里的数字 + 一条从源头测它的命令），故并入批 4 一起落，避免造两个半成品门；本批已把它的全部判据（静态口径、单一声明点、勿引入平台差值锚、从代码面取数）写入 `test-reliability.md`，并交出取数用的代码面扫描器。
- 验收：16 条对照全绿；本仓 8 档测试面全绿；真仓对照——临时加一条 `test.only` 即红（报出档:行与原文），还原后绿。

## 批 4：对账与发布（已完成）

- 靶点：文档宣称的数字可核（一条宣称 = 数字或清单 + 源头命令，失配即红；含批 3 归属过来的账实对照）、门禁下限规则（「只增不减」的机器形态）、发版批纯度（先给出可判形态，给不出就只作评审判据）、阈值单一声明点。
- 动作：`verify-doc-claims.ts`（`count` 与 `list` 两类宣称；命令是 argv 数组、以仓库根为 cwd 运行；`atLeast`／`atMost` 表达下限与上限；**有意不挂台账**——改一个错数比记一笔错账便宜）＋ 负向对照 17 例 ＋ `references/gates.md` 补「宣称值：不自己更新，就让门禁去对账」（三条纪律与诚实边界）与 `governance-model.md` 补「发版批纯度」＋ 接线 `run-gates`（doc-quick 第 10 条）／`bootstrap`（复制校验器、植入空 manifest 与提示，**不入台账家族**）／本仓 `check` 与自用 manifest（两条宣称：doc-quick 门禁数下限、`skills/` 目录清单）。
- 验收：17 条对照全绿；本仓两条宣称绿；真仓双红对照——从门禁表摘掉一门，下限宣称即红（报出「文档说 10，源头测到 9」）；临时新建 `skills/_demo/`，清单宣称即红（报出文档未提及的项）；两处还原后绿。CI 步骤名原先逐个枚举文本门，加门即漂移，现改为指回 `npm run check`——单一声明点的落地。

## 批 5：agent 工作纪律（已完成）

- 靶点：任务书三件（靶点／验收判据／不读面，缺件先问再动）、先定位后阅读（结论锚 `file:line`，不写阅读流水账）、通读即专项（只在作者明示的审计任务下成立，审计只产报告、修复另开靶向任务）、子 agent 并发上限（单波 ≤4，与复核能力绑定）、一个批一个主题、提交与对外文案不引作者指令原文、注释只写约束不写沿革。
- 动作：`references/agent-work.md`（**纯判据，无新代码**——能机器判定的部分本就落在注释门、测试门与宣称值门上，本档只收「没有门禁兜底，靠可指认的偏离来生效」的那些）；SKILL.md 补「Agent 工作纪律」职责节并同步责任边界与描述关键词。
- 验收：文档面过 `verify-md-links` 与 `verify-md-wrap`；`npm test` 与 `npm run check` 全绿。诚实边界已写进档内：这几条都能被绕开，价值在于让越界成为需要解释的事，而不是假装有门。
- 归属调整（结论）：发版批纯度（族四的发布形态）不重复落点，在 `agent-work.md` 里以「一个批一个主题」的一般形态出现并指向 `governance-model.md`；注释口径同理指向 `comment-hygiene.md`，避免同一条判据两处定义。

## 批 6：检查面单点收口（批外补充，已完成）

- 来源（结论）：批 4／批 5 验收后核查出三处「声明与实体不一致」——`check-all` 在交付文档与模板里四处被引用，门禁表里却没有它；本仓 `npm run check` 与门禁表的文本门名单是同一事实的两处声明，且当时并不相等（少 `doc-budgets`，因为本仓没有预算 manifest）；README 手抄了一份文本门标签清单，按批 4 写下的边界属于「抄了就要给命令」而它给不出。
- 靶点：门禁表成为检查面唯一的声明点；模板与文档里以命令形态写下的模式成为可执行承诺。
- 动作：`run-gates.ts` 的门禁脚本路径改为按自身位置解析（`import.meta.url`）——原先是写死的 `scripts/harness`，只对安装布局成立，源码布局下整张表都是「找不到模块」，这既是单点化的前提，也让 README 那句「脚本一律按相对于自身 skill 目录解析」对运行器成立；新增 `text`（文本面全量，`npm run check` 指它）与 `check-all`（全量扩展点）两个模式；`npm run check` 改为跑 `text` 模式，CI 因此也真跑了一遍运行器（此前它只在夹具里被跑过）；三条负向对照进 `run-gates.spec.ts`——命令形态的模式名必须在 `MODES` 里（扫交付文档与本仓 package.json）、`check-all` 必须是其余模式的超集、门禁脚本路径必须是相对自身解析出的绝对路径；`bootstrap.spec.ts` 加一条「模板承诺的两个模式要在自举出来的仓库里真能跑」；README 收编——`npm run check` 一行指向门禁表，手抄清单换成两个数字（`text` 7 道、`doc-quick` 10 道）各挂一条 `atLeast` 宣称，结构行去掉份数；文档同步 `gates.md` 聚合模式节、`bootstrap.md` 的 package.json 段（聚合住在门禁表，package.json 只是壳）、`SKILL.md` 去枚举、模板 AGENTS.md 注明 `check-all` 是扩展点。
- 取舍（结论）：本仓预算 manifest 先声明为空（`{}`）——门跑起来，配额留待「本仓是否自装 harness」定夺，不借本批替作者决定。
- 验收：193 例全绿（+4）；本仓四条双红对照——模板写一个门禁表没有的模式即红、给 `MODES` 加一个不受 `check-all` 覆盖的模式即红、`npm run check` 指向改名后的模式即红、从门禁表摘掉 `doc-claims` 让两条下限宣称同时红（文档说 7 道／10 道，源头测到 6／9），四处还原后全绿。

## 批外补充：本仓不设 CI（已完成）

- 结论：本仓**不设 CI 工作流**，门禁只在本地跑（`npm test` + `npm run check`，提交前自己跑一遍）。采用方仓库要不要接 CI 由采用方定——`project-harness` 的「本地薄、CI 厚」是给采用方的 doctrine，不是本仓的义务。
- 动作：删除自举期加入的 `.github/workflows/ci.yml`（那两步就是 `npm test` 与 `npm run check`）；README 跑测试节写明门禁只在本地跑。
- 后果（诚实记录）：验证面从此只有 Windows 本机（Node 26）。批 6 之后核查出的三项待补——门入口判断对 Node 版本的依赖、`--dry-run` 无覆盖、文档链模板不入目标仓——**没有 CI 兜底**，只能靠本地跑；Linux 可用性不再有自动答案。批 4／批 6 动作行里「CI 步骤名改为指回脚本」「CI 因此也真跑了一遍运行器」是那两批当时的记录，按不改写历史留在原处。
