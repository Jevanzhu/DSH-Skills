# 流程吸纳 执行方案

- 定位：执行正本——批序、每批的靶点与验收、执行记录（末节回填）。**设计理由不在本档**，正本 = [流程吸纳-设计方案-2026-10-13.md](../03-设计/流程吸纳-设计方案-2026-10-13.md)。
- 关系：设计档定族、边界与理由；本档只回答「谁先谁后、每批动什么、怎么算过关」。
- 全局序：**批 1 文档治理 → 批 2 注释卫生 → 批 3 测试纪律 → 批 4 对账与发布 → 批 5 agent 工作纪律**（**已全部完成**，commit 号见末节）。收口条件统一，见设计档 §六：负向对照齐、规则与文档同批、`npm test` 全绿、链上同步记档。
- 批外补充：**批 6 检查面单点收口**（来源是批 4／批 5 验收后的核查）、**本仓不设 CI**（作者决定）、**批 7 发行面收口**（来源是「发行 → 安装 → 使用」轴的核查）、**决策记录判据补齐**与**注释到决策记录的链接判据**（来源是站点同类实践的比对与上游漏项核查）——均不在设计档批序内，见末节。

## 批 5：agent 工作纪律（已完成）

## 批 6：检查面单点收口（批外补充，已完成）

- 来源（结论）：批 4／批 5 验收后核查出三处「声明与实体不一致」——`check-all` 在交付文档与模板里四处被引用，门禁表里却没有它；本仓 `npm run check` 与门禁表的文本门名单是同一事实的两处声明，且当时并不相等（少 `doc-budgets`，因为本仓没有预算 manifest）；README 手抄了一份文本门标签清单，按批 4 写下的边界属于「抄了就要给命令」而它给不出。
- 靶点：门禁表成为检查面唯一的声明点；模板与文档里以命令形态写下的模式成为可执行承诺。
- 动作：`run-gates.ts` 的门禁脚本路径改为按自身位置解析（`import.meta.url`）——原先是写死的 `scripts/harness`，只对安装布局成立，源码布局下整张表都是「找不到模块」，这既是单点化的前提，也让 README 那句「脚本一律按相对于自身 skill 目录解析」对运行器成立；新增 `text`（文本面全量，`npm run check` 指它）与 `check-all`（全量扩展点）两个模式；`npm run check` 改为跑 `text` 模式，CI 因此也真跑了一遍运行器（此前它只在夹具里被跑过）；三条负向对照进 `run-gates.spec.ts`——命令形态的模式名必须在 `MODES` 里（扫交付文档与本仓 package.json）、`check-all` 必须是其余模式的超集、门禁脚本路径必须是相对自身解析出的绝对路径；`bootstrap.spec.ts` 加一条「模板承诺的两个模式要在自举出来的仓库里真能跑」；README 收编——`npm run check` 一行指向门禁表，手抄清单换成两个数字（`text` 7 道、`doc-quick` 10 道）各挂一条 `atLeast` 宣称，结构行去掉份数；文档同步 `gates.md` 聚合模式节、`bootstrap.md` 的 package.json 段（聚合住在门禁表，package.json 只是壳）、`SKILL.md` 去枚举、模板 AGENTS.md 注明 `check-all` 是扩展点。
- 取舍（结论）：本仓预算 manifest 先声明为空（`{}`）——门跑起来，配额留待「本仓是否自装 harness」定夺，不借本批替作者决定。
- 验收：193 例全绿（+4）；本仓四条双红对照——模板写一个门禁表没有的模式即红、给 `MODES` 加一个不受 `check-all` 覆盖的模式即红、`npm run check` 指向改名后的模式即红、从门禁表摘掉 `doc-claims` 让两条下限宣称同时红（文档说 7 道／10 道，源头测到 6／9），四处还原后全绿。

## 批外补充：本仓不设 CI（已完成）

- 结论：本仓**不设 CI 工作流**，门禁只在本地跑（`npm test` + `npm run check`，提交前自己跑一遍）。采用方仓库要不要接 CI 由采用方定——`project-harness` 的「本地薄、CI 厚」是给采用方的 doctrine，不是本仓的义务。
- 动作：删除自举期加入的 `.github/workflows/ci.yml`（那两步就是 `npm test` 与 `npm run check`）；README 跑测试节写明门禁只在本地跑。
- 后果（诚实记录）：验证面从此只有 Windows 本机（Node 26）。批 6 之后核查出的三项待补——门入口判断对 Node 版本的依赖、`--dry-run` 无覆盖、文档链模板不入目标仓——**没有 CI 兜底**，只能靠本地跑；Linux 可用性不再有自动答案。批 4／批 6 动作行里「CI 步骤名改为指回脚本」「CI 因此也真跑了一遍运行器」是那两批当时的记录，按不改写历史留在原处。

## 批 7：发行面收口（批外补充，已完成）

- 来源（结论）：按「发行 → 安装 → 使用」轴核查出四处会让采用方吃亏的缺口——升级会连坐申报（`--force` 把五份 manifest 一起重置）、Node 版本与入口判断的依赖没写进交付面（采用方可能拿到一套「每道门都静默通过」的仓库）、`--dry-run` 的承诺没有对照、文档链模板的提示路径在目标仓并不存在；另加「我装的是哪一版」无处可答。
- 靶点：升级只动该动的；运行前提写明白；承诺与实测对齐；版本可回答。
- 动作：
  - **A1 升级连坐。** `--force` 与 `--reset-manifests` 拆成两个名字：前者只刷新校验器副本，五份 manifest 一律保留；重播 manifest 是独立的破坏性开关（`write()` 增加显式覆盖位，否则重播会被它自己的存在性判断吞掉）。`--force` 运行后打印一行说明自己的覆盖面，把「以为刷了、其实没刷」和「以为没事、其实清空了」两种误解都关掉。
  - **A2 入口判断与运行版本。** `isEntryPoint(moduleUrl)` 的参数改为必填——默认值在本模块求值，会让每道门拿本文件的路径去比，恒假并静默退出 0。版本下限的声明点定为 `package.json` 的 `engines`，`SKILL.md` 写明副本并由宣称钉住，`gates.md` 补「入口判断与运行版本」（含静默绿那条缝隙与两道防线）。
  - **A3 自举承诺的对照。** `structure.spec.ts` 新增「每个随包发布的门禁都能真的跑起来」：逐个启动 `verify-*.ts`，断言至少打印自身名字，找不到任何门禁也判红。`bootstrap.spec.ts` 新增 `--dry-run` 对照：不落任何文件，且计划逐行等于真实运行的产出。
  - **A4 模板定位。** 输出里 `templates/ledger.md` 一类写法改为 skill 侧绝对路径（那些模板有意不复制进目标仓，相对写法会让人去找不存在的文件），配一条对照：输出点到的模板必须在 skill 的 `templates/` 里存在。
  - **B5 版本标识。** `skills/VERSION`（0.1.0，两个 skill 共用一号）＋ bootstrap 每次运行写 `scripts/harness/version.json`（安装方元数据：随内容刷新，不属申报，故不受 `--force` 语义牵连）＋ 输出行打印版本；README 写明版本、两个升级开关与「怎么查自己装的是哪一版」；两条宣称钉住副本（README 的版本 ↔ `skills/VERSION`，`SKILL.md` 的 Node 下限 ↔ `package.json` 的 `engines`）。
- 取舍（结论）：重播 manifest 不做成交互确认，也不并进 `--force`——破坏性动作该有自己的名字，谁签了字一眼可见。版本一处维护（`skills/VERSION`），采用方读到的是副本加一条可核的宣称。
- 验收：203 例全绿（+10）；五条诱导回归逐一变红后还原——`--force` 退回连坐（申报被清零）、`--reset-manifests` 被 `write()` 吞掉（未重播）、`--dry-run` 仍写版本记录、输出点到不存在的模板、版本记录不写真实版本；两条新宣称在真仓各红一次（README 版本改成 0.1.1、`SKILL.md` 下限改成 22）后还原为绿。诚实边界：本批验证仍只有 Windows 本机（无 CI），Linux 侧未验。

## 批外补充：决策记录判据补齐（已完成）

- 来源（结论）：站点同类实践「write-notes-like-deepseek」（czm，同以 DSH 为源、中文单语裁剪）的语义自检清单，比对本仓后确认三条判据本仓缺明文——备选方案的「先写最强理由再否决」、做减法的「已知上限与重访条件」、相对量词的「无基线即降级为事实陈述」。
- 靶点：三条都是**语义判据**，不是机械规则——本批不动 `scripts/`、不加门禁（「这是编辑判断，不是清单」，机器判不出备选方案强不强、基线有没有）。故本批无负向对照，验收以文档面门禁为准。
- 动作：`agent-notes/references/format.md` 的 Alternatives 节补「先写最强理由」并新增「后果要写全，重访条件要有」节；`agent-notes/SKILL.md` 一句话同步（备选写法那行）；`project-harness/references/prose-standard.md` 的「不要做的事」补「不要写没有基线的比较」。
- 取舍（结论）：不做成门禁，也不设「语义自检清单」独立档——本仓的判据按面归位（决策记录格式归 `agent-notes`，散文标准归 `project-harness`），另立清单会造第三份副本。
- 验收：`npm test` 247 例全绿；`npm run check` 7 道全绿（41 份 Markdown 链接与折行、5 条宣称含版本号）。

## 批外补充：注释到决策记录的链接判据（已完成）

- 来源（结论）：上游 `dsh-prose-standard` 要求注释「aggressively link to the owning document for architecture, rationale, algorithms, history」，本仓蒸馏稿全文无「链接」二字——属漏项而非新能力。同源实践另有一套 `// Note:` 锚注释约定与孤儿检测扫描器，评估后不采。
- 靶点：起手改代码的人能看见理由的住处。判据落在注释位置，不做标记约定、不新增扫描器、不动门禁。
- 动作：`project-harness/references/prose-standard.md` 的「内部注释」位补一句——理由的完整版住在决策记录里时就地写结论并点名那篇笔记（用标题或主题），理由本身不复述；点名不写完整路径（笔记路径带日期，会被注释门的日期戳形态判成编年史）。
- 取舍（结论）：**不引入锚注释与孤儿检测**，三条理由——锚注释与本仓注释门的日期戳形态正面冲突（笔记文件名自带日期，探针实测被判成编年史）；笔记在 proposed／implemented／归档之间搬家，精确路径锚会逐次悬空，而代码注释里的路径没有任何门禁在核；上游自身不用锚，做法就是在注释里并入文档链接。丢掉的能力是「哪些笔记一条入链都没有」，等语料规模或一次真实事故证明需要时再上，届时须带 slug 歧义护栏与日期规则的显式豁免。
- 验收：纯判据，无门禁改动，故无负向对照（与批 5 同形）。`npm test` 247 例全绿；`npm run check` 7 道全绿（41 份 Markdown 链接与折行、5 条宣称含版本号）。
